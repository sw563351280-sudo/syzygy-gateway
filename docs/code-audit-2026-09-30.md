# 溯星小屋代码与开屏检查 · 2026-09-30

检查基线：GitHub main `83317fb`。重点检查当前前端入口、启动请求、服务器接口与消费者、数据同步、静态资源和部署脚本；不是对所有业务逻辑逐行验收，也未做线上带真实数据的压力测试。

## 结论

确实有前端移除后仍留在服务器里的功能，也有旧代码副本。但闲置路由和不被加载的脚本通常不会拖慢浏览器开屏。当前更直接的问题是首页初始化依赖聊天/收藏串行加载、提前渲染隐藏聊天、隐藏面板持续轮询，以及主聊天历史全量同步。

## 前端没有入口、后端仍存在的候选项

以下项目不能仅凭“前端没有按钮”就认定绝对无消费者；手机快捷指令、外部 API 客户端不一定在仓库内。此轮没有删除这些接口，也没有清空任何数据。

| 候选项 | 当前状态 | 建议 |
| --- | --- | --- |
| `/capsule-logs`、`/capsule/add` | `server.js:10377` 起仍注册路由；当前 public/tools/scripts/workflows 未发现调用，前端时光信箱逻辑已没有，残留弹窗本轮清理 | 查看一段实际访问日志后退役；保留历史 capsule 数据 |
| `/diary/add`、`/diary/ai-write` | 当前前端无写入调用；但 `/diary-logs` 明确被日历情绪数据读取使用 | 只评估旧写入入口，不删除整个日记模块 |
| `/delete-selected`、`/delete-memory/:uuid`、`/api/restore-all-messages` | 旧 Zep 管理接口；没有 ZEP_URL 时返回 410；当前前端未见调用 | 在确认服务器不再启用 Zep、外部客户端不再使用后整组退役 |
| `/api/flush-zep` | 前端切换/重生成版本、离开页面仍会调用；无 ZEP_URL 时实际不写入 Zep | 先取消/迁移这条兼容调用，再删接口；不能声称已完全移除 Zep |
| `saveToZepWithCounter` | 名字是 Zep，但还调用本地 `appendToTranscript`、实时广播、日记反思调度 | 必须保留本地保存链；后续拆成“本地持久化”与“可选外部镜像” |
| `/api/migrate-blocks`、`/api/migrate-step2*` | 一次性迁移仍作为线上路由保留，未见当前前端入口 | 迁移到显式离线维护命令；先确认迁移状态和恢复方案 |
| 根目录 `script.js`、`server.js.bak` | 旧副本约 81.6 KB、381.2 KB；旧 script 仍包含 exportData/resetAll。实际静态目录为 public，启动入口为 server.js | 可从运行代码树移走，Git 已可保留历史；它们不参与当前首页加载 |

仍需保留：`public/memory.html`、`public/memory-manager.html` 是旧收藏链接的跳转兼容页；`celestial-data.jpg` 被开发中枢背景使用；健康数据、MCP、主动消息有后台/模型工具消费者，不能按前端按钮判断死代码。

## 后续进展 · 2026-10-01

优先级 1 已完成：主聊天首次只同步最近 80 条，滚动到顶部时每次再读取 80 条；局部保存携带历史窗口和版本，服务器保留未加载的旧消息，并在版本或窗口边界不一致时拒绝覆盖。兼容完整同步的旧调用，共创工作区继续使用独立档案策略。新增分页、局部写入、旧消息滚动加载和浏览器回归测试；完整测试 317 项，315 通过，0 失败，2 项平台限定跳过。

## 后续优化优先级

1. **主聊天历史改为分页读取、按版本增量同步。** `GET /api/sync-config` 仍读取完整 JSON 并返回主聊天全部消息；前端显示最近 30 条不等于只下载 30 条。`resyncAndMerge` 双向逐条 some 比较、`mergeMessageLists` 近似去重 findIndex，历史大时有平方级工作量。先把供应商/界面设置与消息同步拆开，再做稳定消息 ID 的增量协议；不能直接把返回消息截短，否则有覆盖/误删历史风险。
2. **音乐空闲轮询降频。** `public/music-player.js:383` 起每 5 秒刷新状态；页面可见时即使没有打开音乐也会继续。建议空闲降频、活动播放/一起听保持现有及时性，或服务端推送。不要直接停掉一起听所需同步。
3. **同步文件 I/O 与首屏归档解耦。** 服务端很多读写仍是 readFileSync/writeFileSync；同步接口还做工作区日期分组和档案比较。下一步测真实文件大小和耗时，将高频读取缓存、持久化串行化；保留原子写入、版本冲突和归档保障。
4. **模型列表缓存与超时。** 每次启动都会请求供应商模型列表；`/api/fetch-models` 未设置自己的显式超时。可按供应商缓存已成功列表，并后台更新，避免模型选择长期停在“连接中”。
5. **拆分前端职责与样式。** 当前主脚本约 263 KB、CSS 约 205 KB（原始字节，非网络压缩体积），有连续追加的旧样式和全屏星空动画。可以按设置/账本/相册拆分，按需加载；动效增加减少动态效果支持，先测移动端 CPU 和视觉回归。
6. **部署/文档同步。** 手动静态发布仍没有覆盖所有早前新增的设置/工作区资源，本轮只补齐自己的两个新文件。建议以后维护显式资源清单。架构文档的行数、旧目录描述与现在代码已有差距；Node >=18 的宽泛要求和旧浏览器测试依赖也应明确支持范围（本机 Node 26 无法运行原 Puppeteer 依赖，内置 Node 24 可运行）。

9,487,176 字节的 `ximai.ttf` 很大，但本轮真实浏览器开屏没有请求它；它只被 note-content/旧日记样式引用。不应把仓库里最大的资源直接当成开屏瓶颈。静态文件缓存/压缩还需要结合实际 Nginx、CDN 响应头确认，不能只从 Express 配置断言线上没有压缩。
